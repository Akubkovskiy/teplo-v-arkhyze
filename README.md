# teplo-v-arkhyze

Публичный сайт базы отдыха «Тепло в Архызе». Этот репозиторий содержит витрину и API для показа домов, цен и доступности. Административная работа с бронированиями остается в EasyCamp.

Документ актуален на 2026-08-25. Перед любыми изменениями в продакшене сначала прочитать этот файл и соответствующий runbook в `ops/`.

## Границы системы

Сайт и VPN используют один домен верхнего уровня, но это разные сервисы и разные точки отказа:

| Сервис | Адрес | Где работает | Назначение |
|---|---|---|---|
| Публичный сайт | `https://teplo-v-arkhyze.ru` | FI, `144.31.185.177` | Витрина базы отдыха |
| Перенаправление `www` | `https://www.teplo-v-arkhyze.ru` | FI | Редирект на основной домен |
| VPN-подписки | `https://kub.teplo-v-arkhyze.ru/sub/...` | DE-E1, `37.46.16.60` | Ссылки подписок и VPN API |
| EasyCamp | внутренний сервис FI | `/root/easycamp-bot` | Источник истины для бронирований, цен и доступности |
| Edge nginx | внутренний сервис FI | `/root/teplo` | TLS, маршрутизация сайта, API и EasyCamp |

`teplo-v-arkhyze.ru` не является адресом VPN-подписок. В конфигурации Marzban зафиксирован отдельный префикс `https://kub.teplo-v-arkhyze.ru`; менять его при ремонте сайта нельзя.

## Продакшен на FI

На сервере FI используются два отдельных Docker Compose проекта:

### Приложение сайта

Путь: `/root/teplo-v-arkhyze`.

- `frontend`: Next.js, только локальный `127.0.0.1:3000`.
- `api`: FastAPI, только локальный `127.0.0.1:8001`.
- `db`: Postgres 16, только локальный `127.0.0.1:5433`, данные в volume.
- API подключен к внешней сети `easycamp-bot_default`.

### Публичный edge

Путь: `/root/teplo`. Это отдельный серверный конфиг, он пока не хранится в этом репозитории.

- контейнер: `teplo-nginx`;
- внешние порты: TCP `80` и `443`;
- сеть `teplo-site_default`: доступ к `frontend` и `api`;
- сеть `easycamp-bot_default`: доступ к `easycamp_bot:8000`.

Критическая зависимость: edge nginx должен быть подключен к обеим внешним сетям. Если убрать `easycamp-bot_default` из `/root/teplo/docker-compose.yml`, nginx не сможет разрешить `easycamp_bot:8000`, а API бронирований перестанет работать.

VPN data-plane на FI использует отдельные порты и контейнеры, среди них Hysteria UDP/443 и Xray TCP/2053 и TCP/2054. Исправление сайта не должно менять их, а также не должно перезапускать `marzban-node-fi-1` или `hysteria2-fi-1`.

## Локальный запуск

```bash
cp .env.example .env
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

Локальные проверки:

```bash
curl -fsS http://127.0.0.1:3000/
curl -fsS http://127.0.0.1:8001/health
```

Локальный `.env` не коммитить и не выводить в терминал. Для изменения схемы или данных сначала сделать отдельный план миграции и backup Postgres.

## Безопасный порядок работы в продакшене

1. Проверить состояние репозитория, контейнеров, сетей и DNS.
2. Понять, меняется приложение или edge nginx. Это разные compose-проекты.
3. Перед изменением edge сохранить `/root/teplo/nginx.conf` и `/root/teplo/docker-compose.yml` в новый каталог `/root/teplo/backups/<UTC_TIMESTAMP>/`.
4. Проверить `docker compose config --quiet` и конфигурацию nginx.
5. Пересоздавать только нужный контейнер через `--no-deps`.
6. Проверить сайт, API, `www`, VPN hostname и старый проблемный маршрут.
7. Проверить логи nginx на новые ошибки `accept4`, `No file descriptors`, `upstream`, `host not found`.
8. Только после этого считать изменение завершенным.

Подробные команды находятся в [ops/deploy.md](ops/deploy.md), [ops/restore.md](ops/restore.md) и [ops/backup.md](ops/backup.md).

## Инцидент 2026-08-25: сайт не открывался

### Что произошло

Старые клиенты retired vpnbot продолжали обращаться к `/ws3780444d`. Edge nginx отправлял этот маршрут в Next.js как обычный frontend-запрос, но без ограничений для WebSocket-запросов соединения держались очень долго. У nginx был soft limit `1024` открытых файлов, который был полностью исчерпан. В результате появились `accept4() failed (24: No file descriptors available)`, таймауты и сайт перестал принимать новые соединения.

Это не было вызвано DNS сайта, VPN-подписочным hostname, Postgres или нехваткой диска/RAM. Прямые проверки `frontend` и API оставались рабочими.

### Что исправлено

В `/root/teplo/nginx.conf`:

- добавлен `worker_rlimit_nofile 65535`;
- `worker_connections` увеличен до `4096`;
- legacy-маршруты `ws3780444d`, `v2ray3780444d`, `dns-query3780444d`, `pac3780444d`, `webapp3780444d`, `adguard3780444d` теперь сразу получают `410`;
- для обычного frontend-proxy заголовки `Upgrade` и `Connection` очищаются;
- таймауты frontend-proxy ограничены 30 секундами.

В `/root/teplo/docker-compose.yml`:

- для `teplo-nginx` добавлен `nofile` `65535:65535`;
- сохранено подключение к обеим сетям: `teplo-site_default` и `easycamp-bot_default`.

Резервная копия, сделанная перед исправлением: `/root/teplo/backups/20260825T120017Z/`. Она нужна для расследования исходного состояния. Это backup сломанной конфигурации до исправления, поэтому не использовать его как обычный rollback без понимания последствий.

### Контрольные признаки исправной системы

- `https://teplo-v-arkhyze.ru/` возвращает `200`;
- `https://teplo-v-arkhyze.ru/api/houses` возвращает `200`;
- `https://www.teplo-v-arkhyze.ru/` возвращает `301` на основной домен;
- `https://kub.teplo-v-arkhyze.ru/` возвращает `200`;
- `/ws3780444d` возвращает `410` быстро, а не висит;
- после исправления в логах нет новых `accept4`, `No file descriptors` и `host not found in upstream`;
- при изменении edge не меняются start time и restart count контейнеров приложения, EasyCamp и VPN.

## Правила для будущего календаря и бронирования

Сайт не должен заводить вторую базу бронирований. EasyCamp остается источником истины для:

- занятых и свободных дат;
- цен и сезонных правил;
- созданных бронирований;
- операций бота, администратора и уборщицы.

Календарь сайта должен получать доступность через API/интеграцию с EasyCamp и не должен записывать бронирование напрямую в локальный Postgres сайта. Перед добавлением оплаты, календаря или новых каналов бронирования сначала описать контракт API, идемпотентность и rollback.

### Текущий контракт бронирования

- `GET /api/houses/{house_id}/availability?days=90` проксирует календарь EasyCamp. Если EasyCamp недоступен, сайт возвращает `503`, а не пустой календарь.
- `POST /api/booking-requests` создает локальную запись и передает ее в EasyCamp с `external_ref` для идемпотентности.
- Успешная передача возвращает `200` и `status=accepted`.
- Временная ошибка или отключенная интеграция сохраняет заявку и возвращает `202` с `status=pending`; retry-job повторяет передачу для статусов `error` и `disabled`.
- Конфликт занятых дат возвращает `409` с понятным сообщением, а запись помечается `conflict` и не повторяется автоматически.
- Фронтенд блокирует отправку, если не получил подтвержденный календарь или выбранный период содержит занятые даты. При `pending` он явно сообщает, что заявка сохранена и требует ручного подтверждения.

Локальная приемка изменений:

```bash
python -m pytest -q api/tests
cd frontend
npm ci
npm run build
```

## Известные следующие шаги

1. Перенести `/root/teplo/nginx.conf` и `/root/teplo/docker-compose.yml` в версионируемый recovery/deploy surface или в отдельный infra-репозиторий. До этого серверный `/root/teplo` считать источником продакшен-конфига.
2. Добавить healthcheck и мониторинг: HTTP сайта, API, EasyCamp upstream, DNS и лимита открытых файлов nginx.
3. Добавить регулярный backup Postgres, `.env`-шаблонов без секретов и edge-конфига с проверкой восстановления.
4. Довести календарь до полноценного визуального выбора диапазона дат и синхронизировать его с единым процессом бронирования.
5. Подключить Яндекс Метрику через `NEXT_PUBLIC_YANDEX_METRIKA_ID`, сохранить UTM первого касания и настроить цели заявок.
6. После стабилизации календаря подключать каналы Avito/Яндекс/посуточно.ру/Островок и считать доходность трех домиков.

## Секреты и безопасность

- Не печатать `.env`, токены Telegram/Marzban, реальные ссылки подписок и ключи в логи, README или git.
- Не менять DNS и `XRAY_SUBSCRIPTION_URL_PREFIX` в рамках исправлений сайта.
- Не выполнять `docker compose down` на продакшене без отдельного плана простоя и rollback.
- Не перезапускать базу, EasyCamp или VPN-контейнеры, если изменение относится только к frontend или edge nginx.
